# kordoc HWPX 시험 성능 측정

측정일: 2026-09-29. 대상: kordoc 4.15.7, HWPX 파싱 후 기존 `HwpHybridChunker` 청킹. **합성 HWPX만 측정**했으며 실제 HWP, 이미지/OCR, 암호 문서는 포함하지 않았다.

## 조건

- 호스트: AMD Ryzen 5 7600 (6코어/12스레드), RAM 16 GiB, Windows + WSL Docker.
- 파서 컨테이너: Linux amd64, 2 CPU, 메모리 2 GiB, 동시 요청 1건, `KORDOC_OFFLINE=1`, 이미지·OCR 비활성화.
- 청킹: Windows Python 프로세스에서 기존 HWP 청킹기를 사용. 시간에는 HTTP 요청, JSON 직렬화·역직렬화, 기존 청킹이 포함된다. 임베딩·검색 인덱싱은 제외한다.
- 합성 문서는 `markdownToHwpx()`로 생성했다. 본문은 서로 다른 식별자를 가진 문단, 표는 **하나의 3열 표**다. 실제 문서의 그림·개체·복잡한 병합 셀을 대표하지 않는다.
- 이 합성 HWPX의 `pageMode`는 `section`이고 모두 1쪽으로 표시된다. 실제 조판 쪽수가 아니므로 쪽당 처리 시간으로 환산할 수 없다.

| 입력 | 본문 문단 / 표 행 | HWPX 크기 | 파서 단독 첫 실행 | 파서 최고 RSS | HTTP 파싱 | 기존 청킹 | 합계 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 소형 | 20 / 10 | 53.5 kB | 0.026초 | 87 MiB | 0.181초 | 3.277초¹ | 3.458초 |
| 중형 | 400 / 100 | 316 kB | 0.082초 | 133 MiB | 0.212초 | 0.270초 | 0.483초 |
| 대형 | 2,000 / 500 | 1.46 MB | 0.278초 | 188 MiB | 0.402초 | 1.197초 | 1.599초 |
| 부하 | 10,000 / 2,000 | 6.28 MB | 0.839초 | 403 MiB | 1.148초 | 6.867초 | 8.015초 |
| 대용량 | 30,000 / 6,000 | 18.83 MB | 2.439초 | 703 MiB | 3.033초 | 22.392초 | 25.426초 |

¹ 해당 Python 프로세스의 첫 청킹이므로 라이브러리·토크나이저 초기화가 포함된다. 같은 프로세스에서 소형 문서를 다시 처리할 때는 청킹 0.025초, HTTP 파싱 0.148초, 합계 0.173초였다.

파서 단독 시간·RSS는 문서마다 새 2 CPU/2 GiB 컨테이너에서 측정했다. 시간은 `parse(bytes, {images:false, ocr:false})` 호출 자체를 재며, 첫 호출 수치다. RSS는 해당 Node 프로세스의 최고 상주 메모리다. HTTP 결과는 별도 2 CPU/2 GiB 서비스 컨테이너와 Windows Python 청킹 클라이언트에서 측정했다. Python 프로세스의 최고 작업 집합은 대용량까지 675 MiB였다. 이 값은 파서 컨테이너와 별개다.

## 해석

- 큰 합성 문서에서는 **기존 청킹이 주된 지연**이다. 6.28 MB 입력은 전체 8.02초 중 청킹 6.87초, 18.83 MB 입력은 전체 25.43초 중 청킹 22.39초였다.
- 6.28 MB 문서의 따뜻한 청킹 경로를 `cProfile`로 분석하니 `count_tokens` 호출이 43,840회, 해당 호출의 누적 시간이 5.80초였다(프로파일링 전체 8.64초, 측정 오버헤드 포함). 그중 토크나이저의 `encode_batch` 자체 시간이 4.26초다. 본문 10,001블록만 청킹하면 6.69초, 표 1개(2,001행)만 청킹하면 0.48초였다. 따라서 이 문서에서는 표보다 본문을 반복 토큰화하는 비용이 크다.
- 기존 rhwp 경로처럼 청킹기 인스턴스를 재사용하도록 시험 코드를 수정했다. 첫 요청의 초기화 비용은 남지만 소형 반복 처리의 청킹은 0.025초였다.
- 2 GiB 파서 제한에서 18.83 MB 합성 문서는 성공했다. **설정된 64 MiB 입력 상한에서의 메모리 안전성은 확인하지 않았다.** 실문서, 압축률이 다른 문서, OCR 활성화는 메모리와 시간을 크게 바꿀 수 있다.
- 같은 수정된 합성 문서를 기존 rhwp Python 코드로 Windows에서 측정한 참고값은 소형 0.117초, 중형 0.294초, 대형 1.393초, 부하 7.723초(각각 파싱+청킹)였다. 실행 환경과 HTTP 포함 여부가 달라 두 엔진의 우열을 판단하는 직접 비교값은 아니다.
- GPU/VRAM은 이 경로에 사용되지 않았다. OCR을 꺼 둔 CPU 파싱과 기존 청킹만 측정했다.

## 벤치마크 해석 주의

kordoc README의 **0.05초/쪽**은 공개 PDF → Markdown 파싱 벤치마크다. 여기서 측정한 HWPX → IR → 기존 Python 청킹 시간과 대상 형식·작업 범위가 다르다. [kordoc 공식 성능 설명](https://github.com/chrisryugj/kordoc)

최초 측정에서는 생성 스크립트가 표 행 사이에 빈 줄을 넣어 2,000행짜리 표가 1행짜리 표 약 2,000개로 생성됐다. 이 입력의 시간·메모리 수치는 위 표에서 **전부 교체했다**. 수정된 문서는 표가 1개이고 실제 행 수를 파싱 결과에서 확인했다.

실제 HWP/HWPX 대표 문서가 준비되면 같은 형식·하드웨어·서비스 경로에서 처리 시간, 최고 RSS, 추출 누락, 청크 수를 다시 비교해야 한다.

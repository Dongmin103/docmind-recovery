# DocMind 개발 인수인계 — 2026-09-23

작성 기준: 2026-09-23, Asia/Seoul. 현재 checkout, 검증 문서, 최근 커밋, 이 대화에서 직접 확인한 브라우저/서버 상태를 종합했다.

## 1. 현재 어디까지 됐는가

**승인된 legacy `.doc` 표본을 Windows에서 복호화하고, Docker에서 변환·OCR·청킹·색인한 뒤 임시 평문을 삭제하고, 전체/폴더/문서 범위로 검색하는 경로까지 실제 검증 기록이 있다.** DocMind 검색 UI도 브라우저에서 열리는 것을 확인했다.

그러나 전체 제품 완성이나 운영 준비 완료는 아니다. 서버 기동·접속 안정성, 실제 UI를 통한 검색과 자료 관리, 세 source의 지속적인 자동 동기화, 클릭 시 임시 원문 미리보기, 답변 생성·개인 대화 이력, 운영 암호화·복구는 각각 남은 확인/구현 범위가 있다.

기능별 구현과 실제 검증 범위가 다르므로 전체 진행률을 임의의 백분율로 표시하지 않는다. 과거 대화의 ‘3번/4번/5번/6번’은 서로 다른 작업 목록에 사용됐으므로 후속 작업은 아래 기능명과 완료 조건으로 식별한다.

## 3. 사용자가 확정한 방향

- All-in-One DC의 암호화 원본이 기준이다. DocMind용 재업로드·매번 수동 복호화를 요구하는 흐름이 최종 목표가 아니다.
- Windows 호스트에서 기존 `uEncryptor2.exe`를 실행하고 Docker에서 파싱·색인·검색한다. 최초 복호화 동시성은 호스트당 1이다.
- 복호화 원본과 변환/OCR 파생 임시파일은 처리 후 삭제한다. 검색용 청크 텍스트·벡터·필요한 관리 정보는 남는다. 파일 삭제를 복구 불가능한 완전 소거로 설명하지 않는다.
- 전체/폴더/선택 문서 검색을 유지한다. 폴더 선택에는 하위 폴더가 포함된다.
- 검색은 저장된 색인을 사용한다. 단순 검색 요청마다 원본을 다시 복호화하지 않는다.
- 원문 확인을 클릭했을 때 임시 복호화·미리보기를 제공하는 방식은 구현·검증 과제다. 영구 평문 원본 저장으로 대체하지 않는다.
- 사용자는 이 장비가 테스트 서버임을 설명했고 기능 확인을 우선하도록 요청했다. 기존 승인 표본의 기능 시험과 Surya 모델 라이선스 수락 이력이 있다.
- Jina 키는 이미 제공되어 외부 비밀 파일 방식으로 연결·검증됐다. 새 키가 없다는 이유로 처음부터 다시 요청하지 않는다. Jina는 검색 결과 재정렬용이며 답변 생성 모델과 역할이 다르다.
- 저장/전송 암호화는 운영 전 완료해야 한다. 기존 격리 시험의 BitLocker 예외를 운영 설정의 일반 예외로 확대하지 않는다.
- 원본 파일 쓰기 기능은 All-in-One의 실제 반영 경로를 검증한 기능부터 공개한다.

### 처리 흐름과 남는 데이터

```text
All-in-One 암호화 원본
  → Windows에서 안정된 버전 확인·작업 claim
  → uEncryptor2로 작업별 임시 복호화
  → 서명된 요청으로 Docker 임시 파서 입력에 전달
  → .doc 변환 / Docling / 필요한 Surya OCR
  → 기존 청킹·BGE-M3 → Elasticsearch 색인 검증·활성화
  → Windows + Docker + sidecar 임시파일 정리 확인
  → 작업 COMPLETE

전체/폴더/문서 범위 + 질문
  → 같은 범위를 적용한 BM25 128 + dense 128
  → RRF(60), 문서당 최대 8, 전체 최대 128
  → 청크별 앞 2,400자 → Jina reranker v3.5 → 최대 5개 근거
```

암호화 원본은 원본 시스템에 남고, 검색 청크·벡터는 ES에 남으며, 작업·버전·매핑은 DB가 관리한다. 신규 클라우드 수집의 임시 입력 경로는 MinIO 영구 원본 저장을 사용하지 않는다. **기존 일반 업로드/미리보기 경로 전체가 같은 정책으로 전환됐다고 보장할 수는 없다.** 자료 관리 UI의 업로드도 원본 클라우드 쓰기 검증과 구분해야 한다.

## 5. 완료된 실제 시험의 핵심 결과

아래 수치는 기존 커밋된 검증 보고서의 결과다. 이 인수인계 문서 작성 중 재실행한 수치는 아니다.

- 승인된 legacy DOC의 실제 재처리에서 Office 이미지 OCR 요청 47회가 HTTP 200으로 완료됐다.
- 활성 청크 집합이 105개/3,305토큰에서 **146개/7,480토큰**으로 교체됐다.
- 최종 작업과 Windows/Docker cleanup이 모두 `COMPLETE`였고, 검사 대상 작업 공간의 임시 평문·파생물 잔여는 0이었다. 암호화 원본은 변경되지 않았다.
- 최종 파싱 상태는 `READY_WITH_WARNING`. 남은 경고는 `LEGACY_DOC_CONVERTED_TO_DOCX`, `DOCX_GEOMETRY_UNAVAILABLE`, `SURYA_MEDIA_EMPTY`다. 각각 변환 사실, Word 좌표 정보 한계, 보조 이미지 OCR의 빈 결과를 의미한다. 필수 OCR 실패를 성공으로 바꾸는 정책은 아니다.
- 실제 전체/폴더/문서 검색 모두 해당 표본에서 최종 결과 5개, 결합 후보 8개를 반환한 기록이 있다.
- 이때 사용한 실제 경로는 `sync-indexed-sources → draft → validate → publish → search`였다. 검증된 카탈로그 ID는 `e182b6d4b69311f18e8a1fff63e6846c`다. 현재 DB 상태가 그대로인지 이번 문서 작업에서 재조회하지 않았다.
- 합성 Office 이미지의 실제 OCR은 75.934초, 정책 경로 재실행은 44.679초였다. 운영 성능 목표나 평균 응답 시간으로 사용하지 않는다.
- Surya는 추론 중에도 `/health`가 응답하고, 추가 parse 요청은 `503 PARSER_SURYA_BUSY`로 거절한다. HTTP 수신을 병렬화했지만 실제 추론 동시성은 1이다.
- Office 이미지 생성 토큰 상한은 1,024, 추론/서비스 watchdog/호출 측 timeout은 600/660/720초로 조정됐다. host-worker lease는 1,800초이며 PDF 기본 동작은 별도로 유지한다.
- 관련 회귀는 작업/보호된 문서/runtime **81개**, Surya/설정/Windows overlay **24개** 통과 기록이 있다.
- Jina 키는 저장소 밖 ACL 제한 파일에서 `JINA_API_KEY_FILE`로 읽고 read-only mount한다. 컨테이너 재생성과 Docker 재시작 후 인증 검색 검증 기록이 있다. 키 값·세션 쿠키·원문은 이 문서에 포함하지 않는다.

## 6. 이번 UI 열기 작업의 관찰과 정정

1. `http://127.0.0.1:18080/docmind` 접속에서 `ERR_EMPTY_RESPONSE`, `ERR_CONNECTION_REFUSED`가 발생했다.
2. 정적 UI가 열렸을 때에도 `DocMindSharedWorkspaceError` 또는 `TypeError: Failed to fetch`가 나타난 시점이 있었다.
3. 컨테이너 시작 시각이 여러 번 갱신됐고, RAGFlow 초기화 로그에 MySQL 연결 거부가 있었다. 이후 DB 연결·마이그레이션·nginx 시작이 진행됐다.
4. 컨테이너 내부와 Windows의 HTTP 200을 확인한 뒤 새 브라우저 탭에서 **공용 작업 공간, 검색/자료 관리/설정, 질문 입력, 전체 문서 범위 선택**이 정상 렌더링됐다.
5. 이 과정에서 애플리케이션 소스나 Compose를 수정해 근본 원인을 해결한 것은 아니다. 반복 시작의 원인이 WSL 수명, Docker daemon, 자원, 다른 실행 작업 중 무엇인지는 확정하지 못했다. 재부팅·유휴 시간 이후 접속 안정성도 미검증이다.

**앞선 설명 정정:** 검색 버튼이 꺼져 있는 것을 보고 ‘작업공간이 비어 있다’고 단정한 것은 잘못이다. 현재 버튼 비활성 조건은 `!query.trim() || explicitScopeEmpty || retrieval.isPending`이다. 질문 미입력만으로도 비활성화된다. 실제 문서 수·현재 활성 카탈로그·자료 관리 API 응답을 확인하기 전 데이터가 없다고 보고하거나 재등록하지 않는다.

검색 홈 렌더는 확인했지만, 이번 브라우저 작업에서 질문을 제출해 결과를 확인하거나 자료 관리의 모든 버튼을 실행한 것은 아니다. 사용자가 자료 관리 화면으로 이동한 사실만으로 해당 기능의 합격 판정을 내리지 않는다.

## 7. 다음 할 일 — 권장 순서와 완료 조건

### 1순위: 기동·접속을 안정화하고 UI에서 기존 검증 데이터를 확인

- WSL Ubuntu/Docker가 유휴 시간 이후에도 유지되는지, 전체 컨테이너 시작 시각이 왜 바뀌는지 조사한다. Docker 이벤트·WSL 로그·프로세스 수명을 근거로 원인을 구분한다.
- DB 및 검색 저장소 준비 전 앱 초기화가 실패하는 경우 시작 순서/재시도/readiness를 확인한다. 이번 MySQL 오류 하나만으로 전체 문제의 원인을 확정하지 않는다.
- HTML HTTP 200 외에 공용 세션 API, 폴더·문서 목록과 앱 내부 API 준비 상태를 확인한다.
- 기존 활성 카탈로그·source·문서가 UI 사용자와 같은 workspace에 연결됐는지 확인한다. 빈 화면을 보고 새 데이터셋을 중복 생성하지 않는다.
- 기존 표본으로 실제 UI의 전체/폴더/문서 검색, 결과·청크 상세, 새로고침, 오류 후 회복을 검증한다.
- 완료 조건: 재접속 후 페이지/API가 정상이고, 세 범위의 검색 결과와 자료 관리 상태가 실제 백엔드와 일치한다. 반복 기동 원인·해결·재현 결과를 남긴다.

### 2순위: 신규 문서가 자동으로 검색에 반영되는 제품 흐름 정리

- **PRD와 현 구현 차이:** PRD 9절은 처리 완료 후 카탈로그 발행 없이 검색되는 흐름을 요구한다. 현재 `docmind_api_service._load_catalog()`는 serving catalog를 읽으며, 실제 시험도 draft/validate/publish를 거쳤다.
- OpenViking 제거와 현재 남아 있는 일반 DB 카탈로그 발행 의존을 구분한다. 과거 검증에 발행 절차를 썼다는 이유로 사용자가 수동 발행을 승인한 것으로 해석하지 않는다.
- 신규 색인 활성화가 안전하게 검색 범위에 반영되는 경로를 PRD에 맞춘다. scope·삭제 제외·활성 버전 검사를 유지한다.
- source/default folder 매핑을 확인한다. 미설정 source의 `ACTION_REQUIRED_MAPPING`을 임의 폴더 할당으로 숨기지 않는다.
- 완료 조건: 승인된 새 표본이 감지→복호화→색인→정리 후 별도 수동 발행 없이 검색되며, 수정·삭제·재시도 시 범위/버전이 일치한다.

### 3순위: 자동 감시·정합성을 실제 운용 조건에서 검증

- 등록된 세 source의 매핑, 실제 실행 계정, watcher 상주 여부, Windows 스케줄 등록 여부를 확인한다. 스크립트가 있다는 것과 상시 실행 중인 것은 다르다.
- 초기 스캔, 추가/수정/삭제, 중복 이벤트, 일부 루트 접근 실패, 00:00 Asia/Seoul 정합성 작업을 검증한다.
- 로그아웃/로그인·재부팅·서비스 계정에서 uEncryptor2와 작업 복구/정리 결과를 확인한다.
- 완료 조건: 부분 스캔 실패가 대량 삭제가 되지 않고, 삭제 문서가 검색에서 빠지며, 오래된 작업이 문서를 되살리지 않고, 임시 평문 정리가 복구된다.

### 4순위: 검색 결과 클릭 기반 원문 미리보기 완결

- 문서 ID·권한·활성 버전을 검증한 뒤 필요한 원본만 임시 복호화한다.
- 변환/전달/렌더링, 좌우 원문·청크 확인, TTL·취소·오류·재시작 후 정리를 연결한다.
- Word 좌표 미제공 상태에서는 정확한 페이지/좌표 강조를 보장하지 않는다.
- 완료 조건: 검색만 할 때는 복호화가 발생하지 않고, 원문 확인 후 임시자료가 정리되며, 삭제/버전 변경/권한 없는 요청이 거절된다.

### 5순위: 답변과 개인 대화 이력

- 검색된 근거를 답변 생성 모델에 연결하고 스트리밍·취소·인용·모델 실패를 검증한다. Jina 키로 답변 생성까지 해결됐다고 보지 않는다.
- 실제 사용자 식별과 개인 대화 소유권을 연결한다. 공용 workspace 계정을 모든 사용자의 대화 소유자로 사용하지 않는다.
- 질문/답변/최소 인용 정보의 30일 조회·검색·만료·복원 시 재노출 방지를 구현/검증한다.
- 완료 조건: 새로고침·재로그인 후 본인 이력을 찾을 수 있고, 다른 사용자 및 만료 이력은 모든 조회 경로에서 제외된다.

### 6순위: 운영 전 필수 검증과 후속 기능

- 대표 한국어 문서/질의로 검색 품질, 검색·색인·OCR·미리보기의 p50/p95, 동시 요청과 Jina usage를 측정한다.
- PDF/Office/HWP/스캔 등 실제 사용할 형식의 회귀 범위를 넓힌다. legacy DOC 성공을 모든 형식 성공으로 확대하지 않는다.
- 실제 TLS, Windows/WSL/Docker 저장 암호화, 비밀 관리·키 회전, 백업 보관 및 RPO/RTO를 적용·검증한다.
- 복구된 DB/ES/필요 저장소와 정확한 앱 이미지로 기준 문서를 검색하는 전체 복원을 검증한다. 기존 marker 복구만으로 이 항목을 완료 처리하지 않는다.

## 8. 이어받을 때 사용할 진단 명령

아래는 설정 검증·상태 조회 중심이다. 설정 파일 전체나 `docker inspect` 전체 결과에는 비밀값이 포함될 수 있으므로 출력 범위를 제한한다. 현재 작업을 인수인계하기 위해 새로 복호화·색인·데이터 초기화를 실행할 필요는 없다.

```powershell
Set-Location C:\DocMindDev\docmind
git status --short
git branch --show-current
git log -5 --oneline

$DocMindDocker = 'C:\Users\uplex\bin\docker.cmd'
& $DocMindDocker compose `
  --env-file .local/docker/windows-dev.env `
  -f app/docker/docker-compose-windows-dev.yml `
  -f app/docker/docker-compose-windows-dev-generationless-e2e.yml `
  --profile full config --quiet

& $DocMindDocker compose `
  --env-file .local/docker/windows-dev.env `
  -f app/docker/docker-compose-windows-dev.yml `
  -f app/docker/docker-compose-windows-dev-generationless-e2e.yml `
  --profile full ps

curl.exe --noproxy '*' -sS -o NUL -w 'http=%{http_code}' `
  http://127.0.0.1:18080/docmind
```

- `docker`가 PATH에서 안 잡혀도 미설치라고 단정하지 않는다. 현재 장비에서는 위 wrapper가 실제로 동작했다.
- wrapper는 `.cmd → wsl → docker`를 거친다. 복잡한 pipe/따옴표를 한 명령 문자열에 넣으면 Windows cmd가 먼저 해석할 수 있다. 가능한 단순 인자 호출을 사용한다.
- HTTP 200은 정적 화면 응답 확인일 뿐, API·검색 준비 완료 판정이 아니다.
- `tools/windows/Test-DocMindGenerationlessE2EReadiness.ps1`는 비변경 준비 검사 도구다. 외부 host-worker 설정 경로가 필요할 수 있으며, 코드에 기대 앱 이미지 digest가 고정되어 있다. 오래된 digest 또는 설정 누락에 따른 실패를 먼저 분류하고 검사를 우회하지 않는다.
- 재기동이 필요하면 현재 사용 중인 두 Compose 파일과 외부 비밀 mount를 유지한다. 기본 Compose만 사용해 답변 모델 gate나 파서 구성을 바꾸지 않도록 한다.
- 이 문서 작성에서는 컨테이너 재생성, source 변경, 새 라이브 시험, 키 회전, commit/push를 수행하지 않았다.

# 임시 원본 미리보기 검증 — 2026-09-28

최신 Office 청크 병합 기준선 `eecdbdf`에서 분리한
`feature/temporary-original-preview` 작업이다. 전체 PDF 변환을 추가하지 않았다.
구현 구조와 적용/복귀 순서는 [구현 안내](TEMPORARY-ORIGINAL-PREVIEW.md)를 따른다.

## 형식 처리 실행 시험

Linux 컨테이너를 read-only, 외부 네트워크 없음, CPU 1개 분량, RAM/swap 상한
1GiB, 임시 파일 공간 256MiB로 실행했다. DOCX/PPTX/XLSX/XLS는 생성한 한국어
합성 문서이며 DOC/PPT/PDF 시험 입력도 합성 Office 문서에서 만들었다.
시험 입력을 만드는 PDF 변환은 제품 미리보기 경로에 포함되지 않는다.

| 입력 | 결과 | 입력 크기 | 형식 처리 시간 | 컨테이너 메모리 관측 최고치 |
|---|---|---:|---:|---:|
| PDF | 원본 바이트 | 19,064B | 0.28ms | 16.34MiB |
| DOCX | 원본 바이트 | 37,023B | 0.77ms | 17.57MiB |
| PPTX | 원본 바이트 | 31,217B | 0.67ms | 17.53MiB |
| XLSX | 원본 바이트 | 6,284B | 0.39ms | 17.25MiB |
| XLS | 원본 바이트 | 5,632B | 0.20ms | 17.24MiB |
| DOC | DOCX | 22,528B | 1,110.84ms | 170.70MiB |
| PPT | PPTX | 622,080B | 1,159.53ms | 171.31MiB |

시간은 단일 작은 표본의 형식 처리만 측정했다. Windows 복호화, API 전달,
브라우저 파싱과 첫 화면 시간은 포함하지 않는다. 메모리는 cgroup의
`memory.current`를 20ms 간격으로 관측했으므로 정확한 순간 최대치를 보증하지
않는다. 시험 후 세션 디렉터리와 변환 임시파일 잔여물은 모두 0개였다.

RHWP 0.8.1은 공개 시험용 HWP/HWPX로 별도 실행했다. HWP 1쪽, HWPX 9쪽 문서의
1·2쪽을 각각 처리했으며 요청하지 않은 모든 페이지를 일괄 생성하지 않았다.
HWP 첫 페이지 0.259초, HWPX 첫 페이지 0.238초·2쪽 0.240초였다.
별도 자식 프로세스 메모리 관측은 각각 36.52MiB와 38.86MiB였다. 위 표의
전체 컨테이너 관측치와 서로 다른 지표이므로 직접 비교하지 않는다.
한컴 프로그램과의 원문 배치 일치 여부를 증명하는 시험은 아니다.

실행 중 확인하여 수정한 환경 문제:

- RHWP 네이티브 라이브러리의 FreeType 심볼 로딩: 기존 RHWP 이미지와 같은
  `LD_PRELOAD` 설정 적용.
- LibreOffice IPC가 `TMPDIR`과 별개로 `/tmp`를 요구: 이미지의 `/tmp`를 공유
  tmpfs 하위 경로에 연결. 별도 디스크나 추가 임시 메모리 공간을 만들지 않음.

## 실제 DOC 원본 연동

기존에 승인해 검증한 DOC 1건으로 수행했다. 본문을 로그나 저장소에 출력하지 않았다.

- 수동 1회 워커: DOC 임시 복호화 → DOCX 준비 → 1,660,779B 수신, **10.384초**.
- 기존 예약 워커의 미리보기 옵션 활성화 후 자동 처리: 동일 경로 **6.223초**.
- 두 시간 모두 브라우저 렌더링을 제외한 생성 요청부터 바이트 수신까지의
  단일 관측치다. 일반적인 문서 처리시간이나 SLA가 아니다.
- 첫 성공 세션을 닫은 뒤 Windows 작업 파일·미확인 cleanup receipt·서버 파일
  모두 0개, DB의 양쪽 정리 상태 COMPLETE, 예약 바이트 0 확인.
- 활성 원본 버전과 청크 집합 그대로, 청크 58개·대상 파싱 실행 4개·수집 작업
  전체 7개·미완료 수집 0개로 시험 전후 동일.
- 미리보기 생성/파일 응답의 no-store와 실제 DOCX 패키지 헤더를 확인했다.

실제 적용에서 드러나 수정한 문제:

- 기존 권한 함수의 DB connection context가 진행 중 transaction을 닫으려는
  충돌: 권한 확인은 transaction 앞에서 수행하고 내부에서는 source/version을
  ORM으로 재검증. 실제 Peewee context를 사용하는 회귀 시험 추가.
- 공통 모델이 create_date를 호스트 시간대로 덮어쓰는 문제: 대기열 제한은
  epoch 밀리초로 계산. 한국 시간 +9시간 조건의 회귀 시험 추가.
- 기존 manualChunks의 locale-config/vendor 순환 참조로 배포 번들이 초기화 중
  실패했다. 강제 분할을 제거한 미리보기 서버에서 검색 홈과 실제 DOC 표시를
  브라우저로 확인했다. 수정 설정을 vite.config.ts에 반영했다.
- 원문 패널에 추가한 세션 래퍼 때문에 기존 section 높이 선택자가 적용되지
  않아 DOC 뷰어가 21,002px로 늘어나고 하단이 잘리는 문제를 실제 UI에서
  확인했다. 세션 아래 뷰어 영역에 flex/min-height/section 높이 제약을 추가했다.
  관련 프런트 테스트 16개와 lint를 재실행해 통과했다.

실제 서버의 부정 요청 검사: 비로그인 401, 열람 토큰 없는 파일 요청 403,
오래된 원본 버전으로 생성 요청 409(SOURCE_VERSION_CHANGED).

수정 번들 브라우저의 문서 상세 진입 시 미리보기 생성 요청 0건을 확인했다.
`원문 보기` 클릭 후 Word 뷰어가 실제 원문을 표시했다. 스크롤 수정 전에는
이미지 51개가 로드돼도 하단이 잘렸으므로 단순 표시 성공으로 완료 처리하지 않았다.
수정 후 표시 영역 316px, 전체 스크롤 높이 20,317px, scrollTop
0→5,824→12,726→16,724→20,001 이동을 브라우저에서 확인했다.
마지막 위치가 전체 높이에서 표시 높이를 뺀 값과 일치해 끝까지 도달했다.
사용자도 화면에서 스크롤 동작을 확인했다. 이후 `원문 닫기`로 종료했다.
이 시험은 Word/한컴 원본 프로그램과 페이지 배치가 완전히 일치함을 보증하지 않는다.

## 형식별 브라우저 확인 범위

합성/공개 문서 QA는 실제 형식별 뷰어 컴포넌트를 사용한다. HWP(X)의 세션 API만
fixture로 대체하여 제한된 processor가 생성한 실제 SVG를 전달했다. 실제 암호화
원본부터 브라우저까지의 전체 경로를 확인한 형식은 위 DOC다.

| 형식 | 확인한 내용 | 한계 |
|---|---|---|
| DOC | 실제 원본 복호화, Word 표시, 문서 끝까지 스크롤, 종료 정리 | Word 프로그램과 자동 페이지 나눔의 일치 여부 별도 |
| DOCX | 한국어 3개 구간, 표, 420×112 합성 그림 로드 | 다양한 실제 문서 표본 확대 필요 |
| PPTX | 한국어 슬라이드 3개, 표, 420×112 합성 그림 로드 | 변환된 PPT의 그림까지 별도 대조하지 않음 |
| PPT | 제한된 processor에서 PPTX 변환 성공 | 변환 출력의 별도 브라우저 대조 미실시 |
| XLSX | 일반 셀·한국어·2개 시트 전환 | 그림의 절대 관계 경로 오류는 수정했으나 그림 포함 표본의 브라우저 대조는 미완료 |
| XLS | 한국어 그리드·2개 시트 전환 | 기존 정규화 경로에서 비트맵 그림이 표시되지 않음 |
| PDF | 합성 텍스트 PDF 표시, 서버 Range 계약 시험 | 브라우저 다중 페이지·한국어·그림 조합 확대 필요 |
| HWP | 공개 1쪽 문서의 실제 SVG 표시 | 원본 한컴 화면과 대조하지 않음 |
| HWPX | 공개 9쪽 문서 중 1·2쪽 표시, 내장 로고 그림, 다음 쪽, 125% 확대 | 나머지 7쪽과 원본 한컴 배치 대조 미실시 |

공개 HWP 표본: [RHWP KTX.hwp](https://raw.githubusercontent.com/edwardkim/rhwp/main/samples/basic/KTX.hwp).
공개 HWPX 표본: [RHWP hwpx-h-01.hwpx](https://raw.githubusercontent.com/edwardkim/rhwp/main/samples/hwpx/hwpx-h-01.hwpx).
표본은 Git에 포함하지 않았다.

그림을 추가한 합성 문서의 추가 processor 실행은 DOC→DOCX 1.23초/212.46MiB,
PPT→PPTX 1.23초/213.14MiB였다. 앞 표와 같은 제약 아래의 단일 관측치이며,
반환된 Office 그림의 재현까지 증명하는 수치는 아니다. 정리 잔여물은 0개였다.

## 적용과 남은 검증

기존 4개 Compose와 source/secret mount를 보존하고 preview overlay를 추가했다.
Windows 예약 워커는 initial_scan_on_startup=false를 유지하며 preview_enabled=true로
활성화했다. source watcher나 정합성 일정은 변경하지 않았다.

앱 이미지 `docmind-ragflow:preview-20260928-validated` (`46308dfe2ebf`),
처리 이미지 `docmind-preview-processor:development` (`fb2e81ea2723`)를 사용한다.
앱을 새 이미지로 재생성한 뒤 API 200, 수정 서비스와 index.html의 SHA256 일치,
자동 워커의 DOC 준비/전달/종료를 다시 확인했다(이 시험 14.415초).

브라우저 첫 화면 시간·최대 heap, 큰 문서/연속 부하, 모든 형식의 그림과 실제
원본 프로그램 대비 배치, 활성 열람 중 실제 프로세스 강제 종료·재시작·네트워크
단절은 추가 검증 범위다. 회귀 시험의 시각 만료/lease 모의 검증과 실제 장애
주입을 혼동하지 않는다. MinIO 호출 횟수를 런타임 추적기로 별도 계측하지는
않았으며, 미리보기 서비스의 의존/호출 경로와 수집·파싱 작업 수 불변을 확인했다.

현재 개발 환경은 공용 로그인을 사용한다. 열람 세션 토큰은 분리하지만
개인별 계정/접근권한 정책이 새로 검증됐다는 의미는 아니다.

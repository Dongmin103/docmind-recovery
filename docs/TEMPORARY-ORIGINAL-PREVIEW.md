# 클릭 기반 임시 원본 미리보기

2026-10-01 고정 자원·대기열 단순화 반영. 검증 결과는 별도 검증 보고서에 기록한다.

## 처리 범위

검색과 청크 조회는 기존 색인을 사용한다. 사용자가 **원문 보기**를 선택하면
등록된 source 문서와 활성 원본 버전을 확인하고 별도 미리보기 세션을 만든다.
Windows 호스트가 원본을 임시 복호화해 전달하며, 서버 수신 확인 후 Windows
평문을 정리한다. 이 경로는 수집 작업·OCR·재청킹·색인을 생성하지 않는다.
원본과 표시 결과를 MinIO에 넣지 않는다.

| 원본 | 표시 준비 | 뷰어 |
|---|---|---|
| PDF | 바이트 전달 | 기존 PDF |
| DOCX | 바이트 전달 | 기존 Word |
| PPTX | 바이트 전달 | 기존 슬라이드 |
| XLS/XLSX | 바이트 전달 | 기존 Excel |
| DOC/PPT | 415 PREVIEW_FORMAT_UNSUPPORTED, 복호화 등록 안 함 | 미지원 안내 |
| HWP/HWPX | 선택한 페이지의 SVG 생성 | 페이지 이동·확대 |

전체 PDF 변환과 영구 원본 캐시는 사용하지 않는다. 기존 DOCX 한글 줄 간격,
Excel 정규화와 시트 탐색은 기존 뷰어가 담당한다. HWP에는 청크와 일치하는
페이지 좌표가 없으므로 정확한 위치 강조를 제공하지 않는다.

## 데이터와 실행 경계

- API는 로그인, 현재 source/문서/원본 버전, 세션 토큰을 검사한다.
  열람 토큰은 헤더로만 보내고 DB에는 해시만 기록한다.
- 현재 개발 환경의 공용 로그인은 여러 브라우저를 같은 인증 주체로 처리한다.
  세션마다 다른 토큰이 추가되지만, 이 기능이 공용 로그인을 개인 계정으로
  바꾸는 것은 아니다. 개인별 접근 정책에는 개인 로그인 구성이 필요하다.
- 처리 중인 수집 작업을 중단하지 않는다. Windows 복호화는 기존 전역 mutex를
  공유하고, 두 대기열이 모두 있을 때 미리보기 3건 다음 수집을 우선한다.
- 원본 버전 변경 시 열람을 중단한다. 원본은 같고 청크 집합만 달라졌다면
  원문을 유지하고 청크를 다시 조회하며 기존 위치 강조를 해제한다.
- 브라우저는 원본 Windows 경로나 임의 변환 경로를 지정할 수 없다.

## 고정 자원과 대기열

- 대기 최대 5건, 120초. 대기 세션은 ID·요청 정보만 가지며 공간 예약과 평문은 없다.
- 준비 중·열람 중 세션 최대 2개. Windows 복호화와 한글 페이지 생성은 각각 1건씩.
- 공유 tmpfs 128MiB 중 공간 예약 예산은 96MiB, 나머지 32MiB는 페이지 교체·관리용이다.
- 일반 형식은 획득 시 64MiB 예약 후 실제 크기로 축소한다. 한글은 열람 내내 96MiB를 예약하므로 다른 원문이 대기한다.
- HWP/HWPX 활성 세션 최대 1개. 원본 최대 64MiB, SVG 한 쪽 최대 16MiB, 마지막 한 쪽만 캐시한다.
- 한글 전용 컨테이너는 CPU 0.5, 메모리 256MiB, 추가 swap 0, 프로세스·스레드 합계 64로 고정한다. 쪽 생성은 최대 60초다.
- 컨테이너 메모리와 공유 tmpfs는 다른 제한이다. 전체 시스템 추가 메모리 256MiB를 보장하지 않는다.
- 일반 형식의 생성·조회·종료·만료는 한글 컨테이너를 호출하지 않는다. API에서 헤더·패키지 검증 후 Windows 평문 정리 확인까지 기다린다.
- 큐 진입과 획득은 모든 프로젝트 행을 일정한 순서로 잠가 전체 배포의 개수·공간 예산을 원자적으로 검사한다. 실행 가능한 요청 중 오래된 순서로 획득한다.
- 한글 페이지 전송 중 다른 페이지 생성을 막고, 중단된 HTTP 획득도 최종 파일·읽기 예약을 해제한다.
- 큐 포화, 대기 만료, 기능 비활성화, 처리 시간 초과, 용량 초과, 서비스 장애를 구분한다. 자동 재요청은 없다.

`preview_memory_128m`는 Docker local volume 형식이지만 driver가 `tmpfs`이므로
일반 디스크 데이터 볼륨이 아니다. tmpfs 삭제는 메모리나 호스트 swap에 대한
복구 불가능한 소거를 보증하지 않는다. Windows 작업 공간의 암호화·백업 제외
정책도 계속 적용한다.

세션은 30초 heartbeat, 마지막 heartbeat부터 2분, 최대 60분 수명을 적용한다.
닫기·실패·만료 후 서버 파일과 브라우저 Blob URL을 해제하고, 재시도는 새로운
세션으로 원본을 다시 읽는다. 정리 실패는 완료로 숨기지 않는다.

## 개발 환경 적용

적용 시점의 Compose 파일 목록과 로컬 mount를 그대로 유지하고
`app/docker/docker-compose-windows-dev-preview.yml`을 마지막에 추가한다.
이 overlay는 원본 수집·OCR·MinIO 서비스를 제거하거나 설정을 교체하지 않는다.
미리보기 실행부는 외부 포트를 공개하지 않는 전용 내부 네트워크에서 동작한다.

1. 변경된 API와 프런트 번들이 포함된 앱 이미지를 준비한다. DB 마이그레이션은 없다.
2. 미리보기 처리 이미지를 빌드하고 합성 표본 검증을 통과시킨다.
3. 현재 Compose 목록 + 미리보기 overlay를 `config --quiet`로 확인한다.
4. 미리보기 처리 서비스를 기동한 뒤 앱만 순차 반영한다.
5. Windows 워커의 새 미리보기 옵션을 활성화하고 승인된 범위에서 확인한다.
6. 원본 해시, 청크 집합, 정리 상태를 확인한다. 전체 소스 수집은 실행하지 않는다.

복귀 시 새 미리보기 요청을 차단하고 세션/Windows 작업의 정리를 확인한 다음
이전 앱 이미지와 워커 설정으로 돌아간다. 기존 원본/MinIO 객체를 삭제하지 않는다.


## 검증과 운영

`app/scripts/benchmark_preview_processor.py`는 읽기 전용 `/fixtures`의 HWP/HWPX를 대상으로 첫 쪽·다음 쪽·이전 쪽 재생성과 cgroup CPU/메모리/PID 및 tmpfs 사용량을 기록한다. 원문 내용은 기록하지 않는다. 운영과 같은 제한으로 실행하며 시험을 통과시키려고 상한을 늘리지 않는다.

Windows 작업자의 기존 `-TimingRoot` 기록에 복호화·검증·전송·정리 구간이 있다. API 큐 대기는 생성→획득 시간이며, 브라우저 첫 화면에는 네트워크 전달과 뷰어 표시 시간까지 포함된다. 컨테이너 측정치를 전체 첫 화면 시간으로 표시하지 않는다.

배포 전에 현재 이미지 ID·Compose 순서·작업자 설정을 비공개 로컬 경로에 보관한다. 수집 진행 건수가 0일 때 처리 서비스→앱→동일 작업자 설정의 `preview_enabled` 순서로 반영한다. 워커 추가 기동으로 복호화 동시성을 늘리지 않는다. 재기동에도 동일 Compose 목록을 사용하는 로컬 기동 스크립트를 보관한다. 장애 시 신규 요청을 차단하고 세션·Windows 평문 정리를 확인한 뒤 기존 앱과 작업자 설정으로 복귀한다. 원본·검색 색인은 수정하지 않는다.

# RAGFlow 기능 축소 조사 및 호환성 검증 계획

조사일: 2026-09-21 · 상태: 백업 소스 정적 조사 완료 / 운영 사용 현황·실행 호환성 미검증

## 1. 범위와 근거

현재 DocMind의 목표는 클라우드 원본 동기화, 임시 복호화·파싱·색인, 폴더/문서 선택, 구성 C 검색, 근거 기반 답변이다. 이 범위를 기준으로 제거 후보를 분류했다. 기능이 현재 요구사항에 없다는 판단과 운영에서 사용하지 않는다는 확인은 다르다.

복구 태그 `pre-openviking-refactor-20260921T061958Z`의 working-tree 백업에서 선별한 코드 2,128개를 읽기 전용 조사본 `source/`에 추출했다. 전체 파일 목록은 `source-inventory.json`, Python AST와 import 조사 결과는 `static-audit.json`, 비밀정보를 제외한 컨테이너 설정은 `runtime-snapshot-summary.json`이다. Python 662개 파일의 AST 파싱 오류는 0건이다. 이는 문법·의존 관계 조사이며 앱 기동, import 실행, 프런트 빌드, 기능 회귀가 통과했다는 의미가 아니다.

운영 DB의 활성 설정, 접근 로그, 대기 작업, 외부 API 소비자를 조회하지 않았다. 백업 이후 운영 변경분도 미확인이다. 애플리케이션 코드 삭제, DB 변경, 서비스 중지·재배포는 수행하지 않았다.

## 2. 유지할 실행 구조

`클라우드 원본 → 변경 감지/재조정 → Windows 임시 복호화 → 문서 파서/OCR → 기존 청킹/BGE-M3 → Elasticsearch → C 검색/Jina v3.5 → 답변·근거`

MySQL은 사용자·권한·문서/경로/버전·작업 상태 등 필요한 메타데이터를 유지한다. Redis 호환 서비스는 작업 큐·락·재시도에 필요하다. 대화 본문·인용 청크 등 내용이 SQL에 저장되는 경로는 별도 보존 정책과 암호화 대상으로 관리한다.

백업 당시 주 앱 설정은 Python API, MySQL, Elasticsearch, CPU였다. BGE-M3, HWP 파서, Docling Office/PDF, Surya OCR, Redis 호환 Valkey, S3 호환 객체 저장소가 실행 상태였다. 컨테이너 실행만으로 개별 기능 사용량을 증명하지 않는다. `docmind-minio-1`의 실제 이미지는 `pgsty/silo` 계열이므로 서비스 이름과 구현체를 구분한다.

## 5. 삭제 전 읽기 전용 운영 확인

1. 실제 실행 이미지/소스 해시와 백업 조사본의 차이 확인.
2. 지식베이스·문서의 parser_id, parser_config, pipeline_id 등 실제 스키마에 맞는 바인딩 조사. GraphRAG/RAPTOR 및 편찬 관련 설정 확인.
3. 답변·embedding·reranker·OCR/VLM 모델 바인딩과 공급자 확인. API 키 값은 수집·출력하지 않음.
4. 등록 커넥터·스케줄과 큐의 대기/실행 작업 종류 확인. 기존 작업 처리·취소·변환 방안을 문서화.
5. 제거 API의 클라이언트·접근 로그·내부 호출부 확인. 특히 SDK, Dify, OpenAI 호환 API는 외부 계약 여부 확인.
6. 기존 객체·썸네일·이미지·SQL 본문·파생 색인의 위치와 보존 정책 조사. 삭제 작업은 목록/수량 dry-run부터 시작.

이 결과 없이 후보 전체를 '운영 미사용 확정'으로 표시하지 않는다.

## 6. 구현 단위와 순서

1. 기존 소스 복구 기준에 더해 DB·ES·객체·이미지의 복원 가능한 시점 백업을 확보한다. 별도 checkout과 별도 데이터에서 진행한다.
2. OpenViking을 제거하고 source/폴더/문서 범위 + C 검색 경로를 먼저 고정한다. 동일 작업에서 청커·embedding을 변경하지 않는다.
3. 불필요한 화면·API·새 작업 생성 진입점을 닫는다. 이미 큐에 있는 작업은 정책에 따라 완료/취소/변환하고 무한 재시도되지 않게 한다.
4. 필요한 공통 클래스·캐시·LLM 호출·파서 서비스를 분리한다. 이어서 에이전트/메모리/그래프/커넥터의 실행 코드와 자동 등록을 삭제한다. UI 숨김만으로 완료 처리하지 않는다.
5. 임시 입력·파생물·정리 경로를 완성하고 MinIO 의존 제거를 검증한다. 모든 사용처가 사라진 경우에만 배포 서비스를 제외한다.
6. 남은 import와 Docker/frontend 빌드를 기준으로 공급자·대체 DB·Go·라이브러리 의존을 축소한다. lockfile과 배포 구성을 함께 갱신한다.
7. 기능별 회귀 통과 후 제한된 운영 전환을 진행한다. 테이블/색인/객체의 물리 삭제는 데이터 복구 검증과 보존 정책 확인 뒤 별도 변경으로 수행한다.

기존 API를 무조건 호환 래퍼로 남기지 않는다. 실제 소비자가 확인된 계약만 명시적으로 이전하고, 제거된 진입점이 성공한 것처럼 응답하지 않게 한다. 단계마다 되돌릴 수 있는 커밋과 데이터 변경 기록을 남긴다.

| 평문 정리 | 성공·실패·timeout·강제 중단 후 Windows/Docker 임시 파일 및 원본/썸네일/청크 이미지의 영구 저장 잔여 없음 |
| 작업 큐 | 폐기 작업 유형 처리와 새 작업 정상, 락/재시도/중복 처리 보존, 완료하지 않은 작업을 성공 표시하지 않음 |
| 외부 계약 | 유지 API의 소비자 회귀와 폐기 API 이전 확인, 제거 라이브러리가 유지 경로에서 로드되지 않음 |
| 성능 | 같은 하드웨어·문서·질의·동시성·캐시에서 기동/메모리/이미지 크기, 검색 p50/p95, 오류·Jina usage 비교 |
| 복구 | 새 환경에서 소스·이미지·DB·ES·필요한 원본 상태 복원, 전환 이후 파일 작업 이력 대조 |

현재 통과 결과는 정적 AST 파싱뿐이다. 실제 삭제 패치가 만들어지면 관련 검증을 실행하고 결과를 기록한다. 기능 수 감소만으로 검색 속도 향상이나 이미지 크기 감소 수치를 보장하지 않는다.

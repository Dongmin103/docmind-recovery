# Windows recovery boot verification

This is an opt-in phase-5 datastore recovery test. It starts only the MySQL,
Elasticsearch, and MinIO volumes named by an authenticated recovery receipt.
It does not attach the original development volumes, production volumes, source
roots, Valkey queues, the application image, or uEncryptor2.

Passing this test proves that the three restored datastores boot with their
backup-time images and contain the expected non-sensitive synthetic marker. It
does **not** prove application startup, document parsing, C-search behavior, or
the PRD acceptance criterion for restoring a reference document and search.
Those remain a separate application E2E test because the recovery package does
not contain or authenticate a DocMind application image.

## Required inputs

- The encrypted `.dmrecovery` package, its public sidecar, and the separate key.
- The restore receipt produced by `Restore-WindowsDevelopmentRecovery.ps1`.
- The ignored synthetic-only environment file used at backup time. The restored
  MySQL, Elasticsearch, and MinIO credentials must match their data.
- A marker receipt created before export and then bound into the encrypted,
  authenticated manifest by `-MarkerPath`. A backup without that embedded marker
  is not eligible for successful boot verification; health alone is insufficient.

The marker receipt contains no credential or document body:

```json
{
  "format": "docmind-recovery-marker/v1",
  "composeProject": "docmind-windows-dev",
  "markerId": "32-lowercase-random-hex",
  "sha256": "sha256-of-the-exact-synthetic-marker-bytes"
}
```

Before the cold backup, the synthetic fixture owner must write the same marker
to all three fixed locations:

- MySQL: `docmind_recovery_probe.markers(marker_id, marker_sha256)`
- Elasticsearch: index `docmind-recovery-probe`, document ID `markerId`, with
  `_source.marker_sha256`
- MinIO: bucket `docmind-recovery-probe`, object key `markerId`, whose bytes
  hash to `sha256`

Pass this receipt to `Export-WindowsDevelopmentRecovery.ps1 -MarkerPath ...`.
Export validates the ignored receipt and copies its marker ID and hash into the
encrypted, authenticated internal recovery manifest. The boot verifier requires
the external receipt and authenticated `manifest.syntheticMarker` to agree;
the package and restore receipt are independently bound by backup ID.

Marker preparation is intentionally not performed by the boot verifier. This
prevents a test from writing a marker after restore and then claiming the backup
contained it. Use only non-sensitive generated bytes and keep the receipt below
ignored `.local/recovery/markers/` or outside the repository.

## Static validation

This command resolves the dedicated Compose file with fake names but starts no
container and opens no volume:

```powershell
powershell -NoProfile -File tools/windows/Test-WindowsDevelopmentRecoveryBoot.ps1 `
  -DockerCommand C:\Users\uplex\bin\docker.cmd
```

To validate a real package, receipt, marker receipt, image set, and disconnected
restored-volume labels without attaching or starting anything, add
`-ValidateOnly` to the full command below.

## Start and verify

Choose four unused loopback ports. The defaults are deliberately different
from the Windows development stack.

```powershell
powershell -NoProfile -File tools/windows/Invoke-WindowsDevelopmentRecoveryBoot.ps1 `
  -PackagePath .local/recovery/packages/dev-20260921.dmrecovery `
  -RecoveryKeyPath .local/recovery/keys/windows-dev-recovery.key `
  -ReceiptPath .local/recovery/receipts/dev-20260921.json `
  -MarkerPath .local/recovery/markers/dev-20260921.json `
  -EvidencePath .local/recovery/evidence/dev-20260921-boot.json `
  -DockerCommand C:\Users\uplex\bin\docker.cmd
```

The verifier fails closed unless all of the following are true:

1. Package, sidecar, and restore receipt backup IDs agree. The external marker
   receipt agrees with the authenticated marker embedded during export.
2. Each restored volume has exact recovery, backup, and service labels and is
   not already attached to any container.
3. The exact backup-time image IDs are present locally. Compose uses
   `pull_policy: never`, so it cannot silently substitute or pull an image.
4. Resolved Compose contains only three services, one internal network, named
   external recovery volumes, and `127.0.0.1` port publications.
5. All three services become healthy.
6. MySQL row, Elasticsearch document, and MinIO object match the marker ID and
   hash. The script does not print their content or credentials.

Evidence contains IDs, ports, status metadata, and the marker hash only. The
temporary decrypted package and generated secret-bearing Compose environment
are removed in `finally`. Successful or failed test containers, the isolated
network, restored volumes, and evidence are never removed automatically.

## Explicit cleanup

Review the evidence, then explicitly remove only its three labeled containers
and isolated network:

```powershell
powershell -NoProfile -File tools/windows/Stop-WindowsDevelopmentRecoveryBoot.ps1 `
  -EvidencePath .local/recovery/evidence/dev-20260921-boot.json `
  -DockerCommand C:\Users\uplex\bin\docker.cmd `
  -Confirm
```

This command retains all restored volumes and the evidence file. Volume removal
is intentionally manual: inspect each exact name and its
`com.docmind.recovery=true` plus `com.docmind.backup-id` labels before running a
separate `docker volume rm <exact-name>`. Never use a prefix wildcard.

If verification fails before evidence is written, the deterministic project is
`docmind-recovery-boot-<first-12-backup-id>`. Inspect resources with that exact
Compose project label and clean them manually; do not run a broad `docker system
prune` or remove any development/production volume.

# AVDC 파서 4개 단회 비교

같은 24개 PDF를 처리했을 때 파서 4개·메모리 2 GiB는 71.862초로,
파서 2개·메모리 1 GiB의 기존 66.684초보다 5.178초(7.76%) 느렸다.
총 파서 CPU 한도는 두 조건 모두 논리 프로세서 4개분이다.
이번 결과는 파서 4개를 상시 적용할 근거가 되지 않는다.

## 코드 변경과 검증

- `KORDOC_WORKERS`와 `KORDOC_CLIENT_CONCURRENCY`가 1, 2, 4를 허용한다.
  기본값은 1이다. 용량 변경 시 프로세스 재시작 요구는 유지한다.
- 기존 서버의 슬롯별 프로세스·시간 제한·정리 로직은 변경하지 않았다.
- 클라이언트 테스트 9개 통과. 2/4개 동시 요청, 초과 요청의 직렬화 전 대기,
  시간 초과, `PARSER_BUSY` 재시도, 정리 실패의 비재시도 등을 확인했다.
- 실제 배포 파서 이미지의 격리 컨테이너에서 Node 테스트 8개 통과.
  2/4개 독립 프로세스, 초과 요청 거절, 충돌·연결 종료·시간 초과·불완전 업로드의 정리를 확인했다.
- Python 검증은 앱 패키지의 무관한 초기화를 격리한 실제 클라이언트 모듈 단위 테스트다.
  운영 의존 서비스를 연결하는 통합 테스트로 해석하지 않는다.
- 제거된 런타임 의존성 검사와 `git diff --check` 통과.

## 비교 조건

새 실제 문서 시험은 4개 조건 한 번만 실행했고, 2개 조건의 기존 기록을 재사용했다.
문서 순서·원본·청킹·임베딩 설정은 유지했다. OCR과 동시 검색 부하는 사용하지 않았다.
두 조건의 색인 시간은 최초 작업 등록부터 마지막 검색용 색인 활성화까지로 계산했다.
워커 종료와 결과 확인까지 포함한 별도 실행 로그는 74.9→79.6초이며 위 지표와 혼합하지 않는다.

| 항목 | 공통 조건 |
|---|---|
| VM | 96 vCPU, 상한 100%, 메모리 64 GiB |
| 임베딩 | 22작업자 × 4스레드, 최대 88개 논리 프로세서분 |
| 기타 서비스 | VM 내부 나머지 8 vCPU 영역; 임베딩 영역과 분리 |
| 문서 처리 | 12슬롯 연속 처리, 임베딩 요청 동시성 24 |
| 파서 총 CPU 한도 | 4개 논리 프로세서분 |
| 변경 | 파서·클라이언트 동시성 2→4, 파서 메모리 1→2 GiB |

CPU 영역 분리는 VM 내부 vCPU 기준이며 물리 코어의 독점 예약이 아니다.
두 코드 파일은 허용값에 4를 추가하는 검증식만 달라진 것을 확인했다.
임시 마운트·해당 환경값·파서 메모리를 제외한 유효 Compose 설정과 임베딩 소스는
이전 시험과 일치했다. 모든 임베딩 작업자와 파서를 사전 예열했다.

OOM·컨테이너 재시작·안전 중단 조건 발동은 없었다.

## 해석과 한계

98쪽 문서의 파싱 요청은 10.229→15.768초, 85쪽 문서는 4.848→8.504초로 늘었다.
파서 컨테이너의 CPU 한도 대기 누적 지표도 1.091→21.262초로 늘었다.
같은 총 CPU 한도 안에서 파서 수를 늘려 자원 경합이 커졌다는 해석을 뒷받침하지만,
해당 지표는 예열을 포함한 누적값이다. 실제 색인 벽시계 시간 손실이나 원인별 기여율로
직접 환산할 수 없다. 임베딩 컨테이너에는 CPU 할당량 제한 대기가 기록되지 않았다.

서버 전체 CPU는 약 6초 간격 표본이며, 서비스별 cgroup 누적 CPU와 측정 방식이 다르다.
그룹웨어 검사는 로그인 페이지 응답으로 실제 업무 부하 전체를 대변하지 않는다.
파싱 요청 시간에는 전송·서버 처리·응답이 포함된다. 임베딩 풀 로그에는 모델 차원 확인 요청도
포함된다. 파서 수와 메모리를 함께 바꾼 단회 결과이므로 모든 문서군이나 더 큰 파서 CPU 한도에서도
4개가 항상 느리다고 일반화하지 않는다.

원 측정 자료는 로컬 시험 기록의 `scale88parser4-24-r1` 디렉터리에 보관한다.
운영 문서·청크·벡터·인증키·실제 설정 파일은 이 저장소에 포함하지 않는다.

## 복원

시험 전 VM 64 vCPU·상한 100%·48 GiB, 임베딩 12작업자·최대 48개분,
파서 1개·총 4개분·1 GiB·클라이언트 동시성 1로 복원했다.
8개 서비스의 자원·환경값이 시험 전 스냅샷과 일치하며 모두 정상 실행됨을 확인했다.
임시 코드 마운트 제거와 원래 클라이언트/서버 소스 해시 일치도 확인했다.
그룹웨어 VM Running·HTTP 200, 활성 색인 작업 0이다.
4개 지원 코드는 저장소에 보관하되 시험 설정은 상시 적용하지 않았다.

## 추가 시험: 파서 4개 유지, CPU 한도만 4→8개분

동일한 24개 문서를 같은 순서로 한 번 실행했다. 기존 4개분 기록은 재사용했다.
파서 4개·클라이언트 동시성 4·2 GiB, VM 96 vCPU·상한 100%·64 GiB,
임베딩 22작업자×4스레드·최대 88개분·52 GiB, 문서 12슬롯과 요청 동시성 24는 유지했다.
실효 Compose 설정과 소스를 대조해 파서 CPU 한도 외 차이가 없음을 확인했다.
파서는 여전히 API·DB 등과 VM 안의 8 vCPU 영역을 공유한다. 물리 코어 독점 예약은 아니다.

| 항목 | 파서 최대 4개분 | 파서 최대 8개분 |
|---|---:|---:|
| 전체 색인 시간 | 71.862초 | 68.480초 |
| 시간당 청크 수 | 68,080 | 71,443 |
| 서버 전체 CPU 평균 / 측정 최대 | 34.55% / 78% | 27.91% / 72% |
| 색인 전 서버 전체 CPU 평균 | 5.62% | 4.85% |
| 그룹웨어 HTTP 평균 / p95 | 14.78 / 19.87 ms | 20.17 / 88.33 ms |
| 색인 전 HTTP 평균 / p95 | 14.66 / 25.07 ms | 12.29 / 22.56 ms |
| 파서 실제 평균 사용량 | 논리 프로세서 1.085개분 | 논리 프로세서 1.055개분 |
| 파서 최고 메모리 | 1,287.49 MiB | 1,404.00 MiB |
| 성공 문서 평균 / 최대 파싱 대기 | 2.107 / 6.571초 | 0.141 / 1.049초 |
| 임베딩 풀 모든 작업자 대기 | 7.197초 | 1.664초 |
| 임베딩 풀 평균 실행 작업자 수 | 7.645 | 8.470 |

전체 시간은 3.382초(4.71%) 줄었고 처리량은 4.94% 늘었다.
최대 허용량을 두 배로 늘린 것이 실제 평균 사용량 두 배를 뜻하지는 않는다.
서버 전체 CPU는 약 6초 간격 표본이고 두 실행의 순간 부하와 표본 위치가 다르므로,
평균 하락을 그대로 CPU 효율 개선량으로 환산하지 않는다.

98쪽 문서 파싱 요청은 15.768→11.578초, 85쪽 문서는 8.504→5.758초였다.
파서 CPU 제한 대기 누적값은 21.262초→0으로 줄었다. 기존 값에는 예열이 포함되며,
이번에는 예열 후와 처리 후 모두 0임을 확인했다. 이 값은 실제 경과 시간 손실과 같지 않다.
한도 완화가 파서 대기를 줄였다는 해석을 뒷받침하지만, 전체 색인 속도를 지배하는 유일한
요인이었다고 볼 수는 없다. 98쪽 문서 청크 생성은 1.906→5.422초였고 임베딩은
15.626→15.556초로 비슷했다. 공유 서비스 CPU 영역에서의 경합이나 실행 순서·스케줄링 영향은
이 단회 로그만으로 분리할 수 없다.

이번 그룹웨어 표본은 기준 13개, 색인 중 11개이며 전부 HTTP 200이었다.
VM CPU 정수 표본은 0%였고, HTTP 평균은 같은 실행 기준 12.29→20.17 ms였다.
p95 88.33 ms는 표본 11개 중 최대인 한 건에 해당한다. 이 표본의 시각은
07:45:00.180 UTC, 첫 파싱 요청은 07:45:07.820 UTC여서 파서 부하 때문이라고 단정할 수 없다.
그렇다고 이 표본을 제외하지도 않았다. 짧은 단회 로그인 페이지 측정으로 실제 그룹웨어 업무의
무영향이나 지속적인 성능 저하를 확정하지 않는다. 안전 중단 조건은 발동하지 않았다.

22건·242쪽·1,359청크 완료, 기존과 동일한 텍스트 없는 PDF 2건 제외, 예상 밖 실패 0건이다.
본문·검색 토큰·위치·순서와 벡터가 기존과 같고 벡터 최대 절대 차이는 0이었다.
원본 해시 유지, 임시 평문 0개, 임시 키 삭제, 워커 종료, OOM·재시작 없음도 확인했다.
워커 종료 및 결과 검사까지 포함한 별도 로그 시간은 79.6→77.6초다. 위 전체 색인 지표와
구분하며, DB 활성화 시각의 초 단위 해상도 때문에 세부 로그와 1초 미만 차이가 있을 수 있다.

원 자료는 로컬 `scale88parser4cpu8-24-r1`에 보관한다.

이번 시험도 VM 64 vCPU·상한 100%·48 GiB와 시험 전 8개 서비스 설정·소스로 복원했다.
재부팅 후 임베딩 12작업자·최대 48개분, 파서 1개·최대 4개분을 확인했다.
그룹웨어 Running·HTTP 200, 활성 색인 작업 0, 보호 조건 발동 없음으로 종료했다.
기존 파서 2개·최대 4개분의 66.684초보다는 1.796초 느리므로 이번 설정을 최적이라고 확정하지 않는다.

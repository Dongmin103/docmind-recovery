# DOCMIND 파일 변경 감지 프로토타입

이번 변경의 목적은 평상시 파일 이벤트마다 source 전체를 다시 읽는 작업을 파일별 처리로 바꾸는 것이다. 구현은 분리된 개발 worktree에서 진행하며, 이 문서는 운영 전환을 실행한 기록이 아니다.

## 처리 흐름

1. Windows 감시기가 설정에 등록된 source 루트의 파일 이벤트를 SQLite 대기열에 저장한다.
2. 변경 중임을 서버에 먼저 전달한다. 서버는 해당 문서의 오래된 인덱싱 결과 활성화를 차단하고 기존 검색 결과는 유지한다.
3. 파일의 마지막 변경부터120초 동안 추가 변경이 없으면 해당 파일의 해시와 식별 정보를 확인한다.
4.10초 뒤 독립적으로 확인한 결과도 같으면 서버가 최신 버전의 기존 수집 작업을 선택한다.
5. 기존 Windows 복호화, 파싱·청킹·임베딩, 검색 색인 교체, 임시 평문 정리 경로를 사용한다.

삭제는120초 대기 대상이 아니다. 루트에 접근할 수 있고 파일이2초 간격으로 두 번 없는지 확인한 다음 확정한다. 파일이 다시 나타나면 수정 후보로 처리한다. 전체 복구 검사에서 목록에 없었다는 이유만으로 삭제하지 않는다.

요청에는 source ID와 상대경로를 사용한다. 드라이브 문자나 실제 호스트 루트는 서버로 보내지 않는다. source 설정은 기존 환경의 값으로 연결하며 예시의 드라이브/폴더명을 코드에 고정하지 않는다.

## 현재 목표와 후속 범위

사용자 결정에 따라 이번 목표는 빠르게 실행 가능한 프로토타입이다. 기본 복구, 영속 대기열, 서명된 통신, 순서·세대 확인과 삭제 보호는 포함한다.

다음은 후속으로 미룬다.

- 전체 복구 검사의 대용량 최적화: 전체 목록 메모리 사용 제거, 디스크 기반 디렉터리 상태, 처리량·우선순위 조정.
-7일 요청/상세 이력 및30일 검사 요약의 자동 정리. 현재 이력은 자동 만료한다고 가정하지 않는다.
-10만 파일 부하,256MiB 메모리 합격 판정, 확대된 MySQL 동시성·실행계획 분석, 모든 장애 조합 시험.
- 운영 감시 작업 교체와 배포.

USN Journal은 사용하지 않는다. 따라서 시작·재시작과 복구 검사의 전체 파일 읽기 비용은 남는다. 평상시 변경 처리와 전체 복구 검사는 구분해서 측정해야 한다.

현재 프로토타입은 폴더 전체 삭제에서 하위 문서의 삭제를 다음 복구 검사로 회수한다. 개별 파일 삭제는 즉시 부재 확인 경로를 사용한다. 폴더 삭제까지 즉시 일괄 반영되는 것으로 판단하지 않는다.

파일 해시는 감시기 프로세스에서 수행한다. 단일 파일의 읽기가 오래 걸리면 세션 갱신이 지연될 수 있으므로 매우 큰 파일의 해시와 임대 갱신을 완전히 분리하는 작업은 추가로 필요하다. 이벤트 수집은 별도 콜백에서 계속한다.

## 개발 확인

기존 호스트 설정에 원본 루트 밖의 `sync_state_root`를 추가한다. 예시 설정은 `tools/windows/docmind-host-worker.config.example.json`이다. 실제 HMAC 키와 루트는 호스트 전용 설정에 두고 Git에 넣지 않는다.

```powershell
powershell.exe -NoProfile -File .\tools\windows\Watch-DocMindEncryptedSources.ps1 -ConfigPath <개발용-호스트-설정.json> -SourceId <합성-source-ID>
```

감시기 프로세스가 바뀌면 새 소유자 ID를 사용한다. 이전 세션 임대가 살아 있다면 이벤트를 저장하면서 최대5분의 기존 임대 만료를 기다릴 수 있다. 기존 SQLite 상태를 삭제해서 이 대기를 우회하지 않는다.

원본과 분리된 합성 source 하나를 사용한다. 감시 시작 후 파일 하나를 수정하고 대기열 병합, 마지막 이벤트 이후 대기, 서명된 API 응답과 해당 문서 작업 생성을 확인한다. 테스트 과정에서 설정된 실제 운영 루트나 기존 컨테이너를 변경하지 않는다.

기존 서비스 회귀와 실제 MySQL 증분 처리 시험은 기준선으로 활용하고, 프로토타입 변경은 영향을 받는 경로의 짧은 확인을 수행한다. 해당 결과는 대용량 성능이나 실제 복호화·검색까지의 종단 간 검증을 대신하지 않는다.

Windows 스모크는 실제 감시기 프로세스와 SQLite를 실행하고 로컬 서명 응답 스텁으로 세션·dirty·독립된 두 upsert·ACK 연결을 확인했다. 실제 DOCMIND 서버부터 복호화·검색까지 전부 연결한 시험과는 구분한다.

서버·복구 검사 확인은61개 통과 후 테스트 보조 코드 오류1개를 고쳐 해당 시험1개를 추가 통과했다. 코드 검토에서 발견한 세션 교체와 구형 API 차단 문제는 별도 시험3개로 확인했다. Windows 대기열·실제 이벤트 수집·서명 통신 스모크가 통과했으며, 검토에서 지적한 핵심4건의 수정 확인을 마쳤다. 이 결과는 로컬 프로토타입 기준이다.

## 추후 전환 순서

서버와 추가 스키마를 먼저 준비한 후, 대상 source의 기존 감시 소유권을 해제하고 새 감시기를 시작한다. 기본 복구가 완료되고 문서 ID와 기존 활성 색인이 유지되는지 확인한다. 같은 source에 구형 작업자와 새 작업자를 동시에 실행하지 않는다.

복원할 때는 새 감시를 중단하고 구형 작업자와 서버 프로토콜 설정을 함께 복원한 후 전체 정합성을 확인한다. 새 서버가 증분 source의 구형 전송을 거절하는 상태에서는 구형 작업자만 다시 켜는 것으로 복원이 끝나지 않는다. 기존 문서·버전·활성 색인과 추가 컬럼은 삭제하지 않는다.
